# 重点标记、公网方案与副露研究口径

本轮继续扩展 PR #3（`phase2-research-engine`），不新建平行应用、不自动合并或发布公网。
标记版本 `decision-flags-1`，研究索引版本 `research-1.1`。更新代码后运行：

```sh
python -m luckyj enrich --data data
python -m luckyj serve --data data
```

只重建研究索引，不重抓原谱、不改原始 SQLite。旧研究库会明确报版本过期，避免新增标签静默缺失。

## 已实现的醒目标记

标记在真实牌名、真实事件顺序中计算，先于任何同形展示。颜色外还有完整文字、边框和说明。列表和详情均显示；牌桌高亮跟切的来源弃牌，立直宣言牌加“立”。单条原样/同形切换不改变标记、计数或原谱。

| 标记 | 计算口径 |
| --- | --- |
| 跟切 | 上次自己切牌之后、本次之前，他家弃过同种真实牌；默认数牌/字牌都算，赤五/普通五归同种。不是把同类非役字任意替换成跟切。保留每条来源的座位、事件序号、宣言标记。 |
| 紧跟 | 来源还是窗口内最近的他家弃牌。只表示顺序，不证明因果。 |
| 立直宣言切牌 | 本次有宣言；不假定下一步立直必然成立，宣言牌放铳也仍是宣言牌。 |
| 立直后切牌 | 此前已经成立立直的后续切牌，独立标记；默认排除不变。 |
| 默听 | 实际切后结构向听0、门清、自己尚未立直、此次也未宣言。暗杠仍门清，明副露听牌不归入默听。未判役、振听、剩余待牌是否为0或是否有足够分数立直，不能当作“主动放弃合法立直机会”。 |
| 新进入/维持默听 | 摸牌前向听>0/等于0，切后处于默听。 |
| 退向听 | 实际切后向听 > 本次摸牌前向听。例：1→2。吃碰后无当前摸牌时不可比较，保持null，不强算否。 |
| 拆听 | 摸牌前0，实际切后>0。 |
| 未取最低向听 | 实际切后 > 此时合法候选的最低值。例：摸前1，能打成0，却打回1；这不是1→2的退向听。 |

这些是重叠集合。同一次可以是“跟切+立直宣言”，或“跟切+默听”。统计区分别给真/假/不可比较计数与全集分母，不画成必须加总100%的饼图。

所有标签可用于 HTTP/MCP 参数（0或1）。新参数：`follow_discard`, `follow_immediate`, `riichi_declaration`, `riichi_locked`, `damaten`, `dama_enter`, `dama_hold`, `shanten_retreat`, `tenpai_break`, `miss_minimum`, `post_call_discard`。旧的 `riichi_declared` 参数保留兼容。

查询 `riichi_locked=1` 时必须明确 `exclude_locked=0`，矛盾条件报错而非产生容易误读的空结果。

## 已实现的副露状态筛选

- `open_melds_min/max`：LuckyJ 当前明副露面子数；加杠算一个面子，暗杠不计入。
- `closed_kans_min/max`：自己的暗杠数。
- `opponents_open_min/max`：已经有明副露的他家人数。
- `post_call_discard`：吃/碰后没有摸牌而直接切牌。不把杠后岭上切牌混进来。

界面、查询定义、MCP及结果事实均暴露相同口径。这些是**切牌节点上的副露状态**，不是鸣牌事件索引，更不是“可鸣而不鸣”的机会库。

## 公网：GitHub Pages 能做什么

官方资料（查阅于2026-09-20）：

- [GitHub Pages 介绍](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)
- [创建 Pages，明确不运行服务端 Python](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)
- [Pages 用量限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- [SQLite 官方 Web Worker API](https://sqlite.org/wasm/doc/tip/api-worker1.md)
- [天凤原谱使用注意事项](https://tenhou.net/man/index.html)

项目站点默认地址形如 `https://zdwnss1.github.io/LuckyJ/`。**这是开通后的地址规则，不是本轮已经部署成功的链接。**代码仓库、Release下载、Pages网站是三件事。现有程序依赖 Python HTTP API、SQLite和指标缓存；只复制HTML到Pages，搜索会请求不存在的 `/api/research/*`。当前绝对静态路径也需适配 `/LuckyJ/` 前缀。

### 路线一：完整研究站（建议优先）

在服务器上部署现有Python查询引擎，网页与API最好同域；或Pages托管前端，显式配置HTTPS API地址。前者避免跨域与双域配置。GitHub保存源码并通过CI发布，不充当持续运行的服务器。

上线前要另做：生产级进程管理/反向代理、HTTPS、访问控制、查询并发和CPU/内存/时长限制、任务队列/预计算、只读语料与可写缓存分离、来源许可审查、原始数据不暴露、监控备份。项目的标准库HTTP服务不应直接当公网生产服务。Pages+API还需精确CORS白名单与API基址，不采用任意Origin放行。

当前MCP是本地stdio；有公网网页并不自动成为远程MCP。远程LLM工具需要另外的受控HTTP工具接口或Streamable HTTP MCP服务，不能把API密钥写进公开前端。

### 路线二：纯 Pages 版

可将查询引擎移到浏览器：SQLite WASM + Web Worker，或把Python计算移植/编译到浏览器。需要单独做浏览器适配、语义交叉测试、数据切片/缓存、内存和手机性能测试；并非开一个Pages开关就完成。当前本机C动态库不能直接装进浏览器。

优点是无需持续付费计算服务器；代价是客户端承担计算和数据加载。可以设计“只发布应用、用户本地选库”的研究客户端；这与匿名用户打开就能查完整语料是不同产品。浏览器要查询静态数据库，访问者原则上就能取得其字节；隐藏下载按钮不是访问控制。

天凤公开手册对原谱使用、一般麻将用途和不特定多数下载服务设有明确注意事项。把全量原库当静态资产直接发布前需确认授权范围；已有Release不代表获得了新用途许可。本轮未开启Pages、未部署API、未添加新的公开原谱下载入口。

## 下一步副露研究：三个不同的粒度

### 1. 场面条件（本轮已做基础）

问：“一副露、二向听、两家立直时怎么切？”仍是 `decisions` 检索。下一步可增加每一家面子结构、吃碰杠类别、来源座位、役牌属性、宝牌位置、是否刚鸣牌等细分条件。

暗手与固定面子必须分开；不能将副露牌揉进暗手计数后匹配。例：暗手 `234m556p678s11z`（11张）+ 一组 `chi(345p, called=3p, from=上家)`。这只是建议的复合查询表示，尚未把它作为新的输入语法实现。同一条记录的暗手、面子、被鸣牌、宝牌/赤牌位置必须共享一套花色/反转/字牌映射。

字牌的役牌属性还要标明相对哪一家：为LuckyJ的役牌不一定为鸣牌者的役牌。按来源座位可以筛“上家提供”“对家提供”，不因换花色而旋转玩家。

### 2. 实际鸣牌事件（下一步）

新增 `call_events`，一行一个真实 `<N>` 事件，键为 `(log_id,event_seq)`。吃、碰、大明杠、暗杠、加杠分别记录；暗杠保留门清。加杠在动作层是一次新事件，在当前面子层只更新旧碰，不能变成两副露。

保留：触发牌及来源、手中消耗的实体牌/赤牌、鸣牌前后暗手、固定面子、向听、分数、立直者、宝牌指示牌时点，以及后续切牌事件链接。吃碰后可展示各合法弃牌的选择；杠有岭上摸牌与新的指示牌时序，不能与“吃碰后直接打一张”采用同一种计算。即使鸣牌后没有普通弃牌节点，真实鸣牌事件也应保留。

于是能问：“第一次吃/碰一般在哪个向听，之后最常打什么？役牌碰以后有多少直接听牌？”统计鸣牌次数、涉及局数、对局数分别给出。

### 3. 可鸣机会及未鸣（随后）

要问“能碰白的时候到底碰不碰”，分母必须包含未鸣机会。当前只存LuckyJ实际切牌前快照不够，需要在他家每次弃牌处重放LuckyJ当时的暗手与规则状态。

枚举合法选项：不鸣、每一种吃法、碰、明杠；自摸触发的暗杠/加杠另用一类机会。喰替、来源座位、已经立直、海底不能鸣等规则在机会层检查，不只看凑不凑得出来。

用 `call_opportunities` 保存触发事件与候选集合；一次机会出现两种吃法仍算一个机会，不扩成两次分母。另记 `resolution`：自己鸣了什么、无人鸣、他家优先动作/荣和阻断、无法确定。若自己可能的吃被他家碰/和阻断，不能记作“LuckyJ主动选择不吃”。不同动作优先级和未显式记录的放弃意图需要保留删失/不确定状态。

比较“吃A还是不吃”时，不鸣分支是保留当前状态等待后续，不应凭空补一摸来凑同样张数。比较“鸣后好处”先做当时可计算的牌理，不拿实际未来摸牌替反事实分支。和率/放铳率等未来结果可以另加结果表，但绝不回灌到当时的可见牌、剩余张数或机会资格。

### 分母示例

同一局很早碰一次，此后切十次：

- 副露状态的切牌样本可能10条；
- 碰牌事件只有1次；
- 该局是否副露只有1个局级观察；
- 能碰的机会可能多次，要从他家弃牌重放。

因此不能用“所有有副露的切牌样本”计算副露率。研究结果必须把状态分母、事件分母、局级分母、可鸣机会分母分清。

## 本轮验收

95项单元/API/MCP/边界测试分别在本地纯Python与C模式通过；全量156,324个决策的新增标签与来源快照、向听标量、SQL字段逐条一致性检查通过，研究库完整性为ok。这不是第二套独立向听算法的正确性证明。详见 `decision-flags-audit.json`，重跑 `python scripts/audit_decision_flags.py --data data`。

本地Chromium不允许直连localhost，明确记录了该失败；随后使用DOM+真实HTTP API桥接完成桌面/手机检查，JS错误0，跟切来源和立直标记检查通过。GitHub CI配置为不使用桥接的直接HTTP验收；其是否完成及结果以提交检查记录为准，不提前声称通过。
